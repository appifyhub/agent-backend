## Context

See `proposal.md` for the motivation and scope. The current `src/di/di.py` lazily caches repositories, services, and bot APIs, while parameterized factories construct provider clients and features for each call. `clone()` currently creates a fresh DI with only database and invoker identifiers. Most return annotations are forward references backed by `TYPE_CHECKING` imports, and the three document-loader factories have no return annotations.

Several useful boundaries already exist: `base_*_client` factories precede usage-tracking wrappers, bot APIs sit below bot SDKs, and attachment storage has a protocol. `LocalAttachmentStorage` accepts a directory. `test/db/sql_util.py` already supplies SQLite-backed repositories, although initialization changes the module-global database engine/session factory. Message-burst work calls `get_detached_session()` directly before cloning DI. HTTP calls, SDK construction, process execution, configuration, and time access are not uniformly routed through DI.

The inventory contains 120 test modules: 22 have at least 500 lines, and 98 are smaller. The module list in `tasks.md` is the migration ledger. Existing repository and pure-function tests need a compliance review, not invented external fakes. Many current mock assertions encode real requirements, including no external work on cache hits and charging only for successful provider calls.

## Goals / Non-Goals

**Goals:**

- Preserve the production DI API and default behavior while adding one optional interception mechanism.
- Keep fake registration, annotation resolution, canned external behavior, and resource setup in test support. Name all fake implementation modules `fake_*.py`.
- Prefer normal components whenever they work in the isolated offline environment; add fakes only for a concrete unmet need. Use real repositories backed by isolated SQLite in service and repository tests.
- Make each milestone independently verifiable and understandable as a complete slice.

**Non-Goals:**

- A DI subclass, mocked DI behavior, general-purpose dependency injection framework, or permanent DI patches. The managed test helper's scoped initializer forwarding is the sole DI patch described below.
- Rewriting the subject's business decisions inside its collaborators' fakes, or building a general SQLAlchemy/database emulator.
- Asserting on repository or database internals from service tests, or implementing fake SQLAlchemy sessions and query evaluation.
- Changing production code to enable more tests, add test getters, or expose internal behavior for assertions.
- Simulating entire vendor SDKs, adding live-service tests, changing public application APIs, or modifying production database schemas.
- Claiming that SQLite proves PostgreSQL row-locking or concurrency behavior.

## Decisions

### 1. An optional interceptor on the existing DI

Add an optional interceptor constructor argument without changing existing positional arguments. Use a small common wrapper for dependency-producing methods and property getters; keep their ordinary construction bodies. The request supplied to the interceptor carries the requesting DI, provider identity, declared return annotation, and invocation arguments. The wrapper does not need to resolve imports or know any fake classes. The interceptor returns a replacement or `None`; test-side composition handles per-test overrides followed by shared defaults.

Interception covers resource/service construction. Context readers and setters, `db`, `invoker`, nullable chat access, rollback, cloning itself, and metadata-only methods are not intercepted as dependency factories. Add missing annotations to resource factories so all applicable construction points can participate. Do not intercept arbitrary attribute access through `__getattribute__`.

Production DI uses only its explicit interceptor argument. `di_utils.py` owns `context_local_interceptor`; `di_for_tests()` sets its ContextVar token and temporarily wraps `DI.__init__` to supply that argument when omitted. The real initializer still executes. The helper restores both the enclosing context value and initializer on normal exit or failure. Existing containers retain their captured policy; nested test environments affect only new construction. Explicit constructor interceptors take precedence, including a passthrough interceptor when a test needs ordinary production construction inside the offline environment. This carries replacement policy, never a DI instance or an application session. Python's `asyncio.to_thread` propagates the execution context; plain `Thread` does not. Media tests use a shared test-side thread helper that runs real worker bodies in a copied context, gates execution for acknowledgement assertions, and joins workers before test resources close.

Only `result is None` permits fallback. Errors propagate; a valid false-valued replacement is handled. Production never imports test support, and the no-interceptor path does not resolve annotations or build a registration registry.

Alternatives: a typed constructor bundle was discussed, but return-type interception is the user's chosen API. A DI subclass is explicitly excluded. Broad attribute hooks would also affect context operations and obscure normal construction.

### 2. Resolve declared types in test support

Place the helper and resolver under `test/util/di_utils.py`, with behavioral implementations under `test/fakes/fake_*.py`. The test-side registry uses canonical type identities and accepts fixed instances or factory callables. Evaluate annotations available in the provider's runtime globals, including the parameterized `AbstractContextManager[Session]` key; retain lazy import lookup for unavailable forward references. Resolve raw forward-reference annotations only for registered replacement types. Read the provider module's import declarations, including `TYPE_CHECKING` imports, to map third-party aliases such as `GoogleSDKClient` to their qualified source. Cache that test-side lookup and compare actual type identities; never treat an unqualified class name as globally unique.

This allows a test registration to refer to the production contract even when the implementation is a differently named fake. Unregistered construction paths return `None` without eagerly importing every DI return type. The resolver can bind arguments against the provider signature for a consistent factory request, including defaults, positional arguments, and keyword arguments.

Alternatives: eagerly evaluating every annotation would encounter missing `TYPE_CHECKING` imports and circular dependencies. Requiring every DI factory to import its return type at module load would expand the production import graph solely for tests. Source-derived test-side aliases keep that complexity local and reviewable.

### 3. Preserve lifetimes and clone context

Mark wrapper use according to each provider's current lifetime. A cached provider checks its instance before invoking interception; cache an override once in that DI, using a provider-specific slot rather than a type-wide global cache. A transient provider invokes interception on every call with current arguments. Existing global/singleton providers retain their current scope on the production path; test replacements remain owned by the environment.

Install the interceptor at construction and do not promise hot-swapping registrations after dependencies have been resolved. No cache invalidation API is needed. Clone the replacement policy, not cached repositories or services. Factory callbacks receive the clone, so contextual replacements can bind to its session and invoker. Fixed external fakes can deliberately share an outbox or response state across clones in the same test environment; they must not retain a parent's session-bound service graph.

Alternatives: copying the instance dictionary during clone would reuse stale sessions. A single instance cache keyed only by return type would incorrectly share parameterized feature objects.

### 4. A resource-owning test helper

Expose `di_for_tests(interceptor = ...)` as a context manager yielding a real DI. Tests using `unittest.TestCase` can enter it through their existing cleanup facilities; other tests can use a `with` block. Supply invoker and chat identifiers when needed, seed collaborators through public interfaces with existing stubs, and obtain subjects through the normal DI API. Pure functions and value objects do not need a container; model objects still come from stubs. Resource mechanics belong to test support, not service-test setup or assertions.

Repository tests obtain real repositories from `di_for_tests()` using its isolated SQLite database. Their migration replaces SQLUtil setup, preserving repository behavior and assertions. No fake session, SQL evaluator, alternate database argument, or production repository changes are needed. Service tests also use normal repositories where suitable and do not configure or inspect sessions.

Generic SQLite setup stays in private helpers in `test/util/di_utils.py`, its only consumer. It uses the shared metadata base without concrete model imports, a model catalog, field names, row inspection, or data-generation callbacks. The helpers use SQLAlchemy's already-registered `BaseModel.metadata`, as production initialization does. Existing test imports register the schema, so no package scanner or extra class resolver is needed. The SQLite setup copies that metadata and maps declared identity columns to SQLite's native integer primary keys, retaining the original keys as unique constraints. SQLite allocates values itself. Production metadata, ORM mappings, and database globals remain unchanged; service tests contain no database adaptation logic.

Tests configure the helper's existing default fakes through the DI API rather than constructing and registering another copy. HTTP, S3/Uploadcare clients, Telegram/WhatsApp APIs, OpenAI/Google/Replicate/xAI base clients, the base chat model, and URL shortening have shared per-environment defaults. Application services, bot SDKs, commands, tool wiring, and repositories remain real. Tests retrieve `FakeChatModel` through `base_chat_langchain_model()` and queue their responses. DI composes `chat_langchain_model()` from that base model and the real usage decorator, following its existing base-client/decorator pattern. Tests retrieve `FakeUrlShortener` through `url_shortener()` and configure the returned link when needed. These test setups need no additional interceptor, HTTP mocks, or vendor-constructor patches. Custom interception is for behavior that differs from shared defaults or tests of interception itself. Default HTTP and model fakes never perform network I/O and reject unconfigured requests or exhausted responses.

The environment owns a temporary storage root, isolated SQLite database, and fresh default fake state. Service tests use suitable real repositories and observe saved state through public repository getters. They neither configure nor validate database/session behavior. Repository tests stay at the repository layer, independently of service tests. Use real `LocalAttachmentStorage(root = ...)` for storage behavior, initialize it explicitly, and register it for the `AttachmentStorage` contract and the local-storage factory's default root. This supplies local storage without changing configuration. Storage-selection tests explicitly invoke the original selector through their interceptor and replace the concrete backend factories. Tests can also override the `AttachmentStorage` contract directly.

Replace `SQLUtil` as its consumers migrate: production DI constructs each subject while test support owns the isolated resources and fake state. Do not retain a second repository factory API or change production database globals. The user approved an uncached `DI.new_session()` adapter adjacent to `db` and rollback. It returns the existing `db.sql.get_detached_session()` context manager; SQL creation and cleanup remain unchanged. Test DI registers fresh real SQLite session scopes on the environment's database. Background integration must preserve the archived burst design: timers retain sessionless contextual DI, and claim, processing, and finalization have separate session scopes. Media workers must never retain request DI. Propagating a session-bound parent container into background work is not an acceptable interception mechanism. The responders retain their original signatures and each create one ingress DI. They open `di.new_session()`, attach its yielded session with `di.inject_db_session(db)`, and then resolve the inbound service. Initial injection does not own cleanup and rejects an already attached session, protecting cached repositories from stale session bindings. The invoker and chat are injected after ingestion resolves their internal identities. Burst claim, processing, and finalization use the contextual DI's adapter inside the existing `with` blocks. The scoped interceptor therefore reaches the unchanged sessionless coordinator and thread-pool workers without carrying request resources. `main.py` and SQL helpers remain unchanged. Image and video workers create fresh DIs inside the worker, use `new_session()` and initial session injection, and retain separate generation and failure-notification scopes. Their rollback behavior and sessionless thread handoff are preserved. The final milestone must audit remaining `SQLUtil` references and competing database setup, migrate remaining consumers, and delete `test/db/sql_util.py` before running the full suite. Previously migrated SQLite-backed repository tests remain valid.

Close background work, sessions, and engine resources before deleting temporary files, including on exceptions. Tests that need configuration changes set public `config` properties directly and restore only the values they change using local cleanup, including after failure. Do not add global configuration initialization or restoration fixtures. Opening or closing DI environments, including nested environments, must not reset settings or reload configuration. Preserve a way to select a real adapter in its own tests while still replacing its lower-level transport. Shared defaults are per-environment registrations, not a permanently enabled fake for every application class.

Alternatives: a global test DI would leak state. Reusing the current global session factory without lifecycle control could couple unrelated tests and background work. Replacing every collaborator would unnecessarily duplicate working application behavior.

### 5. Keep normal components and fake only what needs replacing

Attachment-processor tests retain real vision, audio transcription, document search, loaders, storage, and cache repositories. Shared OpenAI support replaces only the base client, with explicitly configured transcription responses and embedding vectors; its usage wrapper remains real. The HTTP fake accepts explicit URL patterns for signed download links, retaining strict failure for unmatched requests. Direct requests.get/post calls use the same environment-owned HTTP fake through scoped transport forwarding in di_for_tests(), because those production paths do not obtain HTTP through DI. Tests configure the existing GET or POST response queues through di.http_client(); no per-module HTTP patch or requests-mock is needed. The hooks restore the enclosing transport on exit or failure, and the socket guard still rejects other live traffic.

Do not make a change unless it is needed. Check whether the normal component works in the isolated offline environment before introducing a replacement. A dependency is not a reason to fake it. When external access, a controlled failure, or another concrete limitation requires a fake, implement only the operations the scenario consumes. Keep signatures aligned with the production contract. Use stub factories for structured responses, including vendor response types currently represented by generic mocks. Fakes expose concise configuration and meaningful observations such as requests, sent messages, files, and queued failures. Unexpected requests and exhausted queues fail with useful diagnostics. Fakes can record interactions when ordering or absence of an effect is itself the behavior under test.

| Boundary | Consumer tests | Tests of the boundary implementation |
| --- | --- | --- |
| Platform SDKs and bot APIs | Real SDKs with shared bot API fakes configured through normal DI providers | Real SDK with fake API; real API with fake HTTP transport |
| Attachment storage | Real local disk storage in a temporary directory | Real S3/Uploadcare adapter plus an injected client fake |
| AI/model clients and accounting | Fake external clients; retain suitable normal accounting collaborators | Real wrapper with fake provider and normal accounting where suitable |
| HTTP | Fake client with method/URL/request-aware responses | Real fetching/retry/cache logic against that fake |
| Video processes | Real application wrapper with a fake process runner where practical | Narrow mocks of system process/filesystem primitives only when a fake cannot reasonably express the failure |
| Repositories and database access | Normal DI repositories with isolated SQLite; fake only for a concrete unsupported scenario | Real repository with the existing isolated SQLite environment |

Keep the class under test real and stay in its layer. Assume its dependencies work; test their implementations in their own unit tests. For example, membership service tests supply membership response stubs to the shared bot API fake, execute the service with the real SDK, and inspect membership values through public getters. They do not assert Telegram parsing, track sessions, or verify rollback/SQL ordering. Executing a real collaborator does not mean testing its internals. Pure value/model logic remains real.

Use existing production interfaces and test-side injection. The consistency review specifically authorizes separating base-model construction from its accounting decorator in DI; this is not permission for broader production refactors. Otherwise, do not change production constructors, methods, getters, or dependency boundaries solely to enable tests. When a result has no public getter, a getter may be added to a test-only fake; if meaningful verification is still impossible within the subject's layer, omit that assertion or case. Do not compensate with deep instrumentation, call traces, or tests of dependency internals.

Reuse the existing S3 fake's useful behavior after extracting it to shared support. Do not implement unconsumed portions of vendor APIs or a generic framework for programming arbitrary fake methods. Add required operations in the milestone that first consumes them, and validate fake contracts through the actual consuming tests.

Alternatives: replacing the subject would bypass the behavior under test. Blanket replacement of the dependency graph would duplicate working normal components and create unnecessary maintenance. Mechanical conversions from `Mock` to objects with arbitrary `return_value` attributes would retain the same brittle test design.

### 6. Review every module and preserve behavioral assertions

For each assigned module, first inspect its production subject, then identify its layer, public behavior, and direct collaborator contracts. Obtain DI-managed subjects through the real test DI, seed valid data with stubs, retain suitable normal collaborators, and add shared fakes only for concrete unmet needs. Verify returned values and results available through public getters. Service tests stop at the repository interface; they do not validate SQL, sessions, rollback, or repository implementation. A test-only getter is acceptable; adding production observability or crossing layers to retain an old mock assertion is not.

Verify necessary fakes through observable consumer behavior. Existing core DI coverage is sufficient for ordinary migration work. Add DI tests only when introducing a special production DI feature whose failure could break application behavior. Do not add DI tests for ordinary dependency construction, fixture behavior, or test-helper implementation details, and do not relocate redundant cases into another test module.

Remove all mocking and monkeypatching of owned behavior, including wrapped spies, repository method reassignment, mocks of data objects, and config mocks. The only test-harness exception is the scoped initializer wrapper described above: it forwards the interceptor argument and executes the real initializer without replacing application behavior. Module-level configuration scenarios can use actual configuration values with scoped restoration. System clocks, sleeping, process failures, and truly unreplaceable external dependencies can retain narrowly scoped system-level mocks with a specific rationale. An inconvenient constructor does not authorize a production refactor or an owned-code mock; use existing interfaces and keep verification at the subject's layer.

Record the reason and target for each remaining exception in its relevant test and in the milestone review. This requires no new inventory document. A final search must examine aliases, decorators, `patch.object`, monkeypatch helpers, and assignment of mock methods, not merely imports of `Mock`.

Alternatives: banning every system mock would force unnecessary abstractions. Leaving owned-code mocks as temporary exceptions at a completed milestone would violate the agreed completion criterion.

### 7. Deliver complete milestones and update rules last

`tasks.md` names each current module exactly once as primary migration scope. The foundation includes a small coherent storage/DI test group. Review batches follow feature boundaries and actual diff complexity, not a fixed source-file length. Related sections can share a user-approved review batch. Feature repositories stay with their feature modules; caches and shared infrastructure form a separate batch. Shared test support belongs to the consuming milestone; production edits for testability are prohibited. An earlier module can receive a necessary regression update later without treating its original migration as incomplete.

Each milestone has implementation, verification, and a separate manual-review gate. On completion, stop and present the affected scope, checks, and any permitted exceptions in chat. Leave the approval task unchecked until the user explicitly approves continuation. A request to revise the current milestone does not authorize the next one. This review contract applies even if the implementation tool would otherwise continue automatically.

For changed Python files, run the required Ruff and spacing commands. Run affected tests through `pipenv run pytest -v` from the project root with no live external dependencies. Run the full offline suite at final completion and sooner only when shared infrastructure changes require broader regression coverage. No database migration is involved.

After module migration, a separate parallel-execution milestone will add pytest-xdist through pipenv and verify shared-resource isolation before changing defaults. Compare full serial (`-n 0`), two-worker (`-n 2`), and automatic-worker (`-n auto`) runs, including repeated parallel runs, collection parity, cleanup, timings, and available local/CI resource limits. Process-local config and singleton state do not establish filesystem/database isolation between workers. Enable automatic workers only after verification, preserve serial and fixed-count overrides, and stop for manual review before the final milestone. No parallel-execution changes are part of the current caches/shared-infrastructure batch.

The final milestone repeats the module inventory and searches all active visible/hidden agent rules for the old test policy and equivalent wording. Read each applicable rule file in full before editing it, then add a concise testing subsection consistently to the six known rule files and any additional active matches. Explain `self.di = self.enterContext(di_for_tests())` in `setUp`, automatic cleanup on success and failure, and the equivalent context-manager form. Cover shared stubs for data/model objects, real production DI, unit boundaries, default fakes and explicit overrides, no unnecessary changes or fakes when normal components work, isolated SQLite for real repositories in service and repository tests, temporary disk storage, offline operation, narrow system/external mock exceptions, local configuration cleanup, and class-level type declarations for every `self` attribute assigned in constructors or test setup. Preserve historical OpenSpec records and unrelated instructions. Defer this rule-file work until the final milestone.

The testing subsection must explicitly show registering `self.addCleanup(setattr, config, "web_retries", config.web_retries)` before changing the public property. Explain that this restores the original value even if setup or the test fails; mutable dictionaries require restoring their contents, and tests that change environment or singleton state must restore that state locally. Do not add global config-reset fixtures. Also document the verified parallel command and serial/fixed-worker overrides.

## Risks / Trade-offs

- **Forward references or aliases select the wrong fake** → test normalization, qualified-name collisions, unhandled types, and alternate calling styles in the foundation; avoid eager import traversal.
- **An overlooked dependency reaches a live service** → deterministic test configuration, shared fake defaults for required external boundaries, and a test-only network prohibition as a system-level guard. A missing replacement fails visibly instead of making a request.
- **A unit test asserts on unrelated application layers** → keep setup and assertions on public collaborator contracts; retain normal components where suitable and use a fake only for a concrete scenario need.
- **Cloned/background DI uses stale services or the wrong database** → independently verify parent/clone caches, detached sessions, shared external observations, and cleanup after worker completion.
- **Fakes drift from external contracts** → use concrete response models and narrow interfaces, exercise real adapters with fake transports, and grow only the consumed SDK surface.
- **Assertions weaken during migration** → preserve an identifiable result/state/effect assertion for each meaningful original case, including failures and absence of work.
- **SQLite differs from PostgreSQL** → retain existing database-specific assumptions explicitly; the change does not certify locking behavior.
- **A nominally small milestone grows** → keep its assigned modules whole, include only necessary support, and agree on an adjusted slice during review before expanding into other modules.

## Migration Plan

1. Establish the foundation and verify the interceptor, test environment, and existing local storage through the first complete slice. New test-module creation still requires the confirmation mandated by the current project instructions; prefer suitable existing test modules where practical and ask before adding a new test file. Helper/fake modules are support code, not new collected test modules.
2. Execute the dependency-ordered module milestones in `tasks.md`, stopping at every manual-review gate. Build additional fakes and external construction points as their assigned tests require them.
3. Verify parallel execution in its own review milestone, then complete the inventory/mock audit, update agent rules, and run final offline verification in serial and parallel modes. Include modules added while the migration is underway.

The optional production hook is backward compatible, so existing tests and consumers can coexist during migration. If a reviewed slice needs rollback, revert that slice and its exclusively used support while preserving already reviewed milestones; do not remove shared support still used by earlier slices. No deployment or data migration step is required for this proposal.

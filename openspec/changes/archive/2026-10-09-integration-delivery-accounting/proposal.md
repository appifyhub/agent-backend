## Why

Paid messaging delivery must be accounted for independently from model usage, and WhatsApp work must not begin when the invoking user cannot fund one outbound response. New users also need their welcome credits before their first pre-EULA response can pass that delivery check.

## What Changes

- Preserve the currently staged delivery-pricing, delivery-identity, usage-record, outbound-charging, and sequential WhatsApp `sent`-receipt implementation as the authoritative foundation.
- Add a delivery preflight that requires the payer to fund one complete outbound message: in a private chat this is the non-agent recipient, and in a group it is the sum for every non-agent member.
- Run stateless delivery preflight once at each execution owner before command, model, generation, or notification work that can produce a paid outbound message. BYOK users remain subject to delivery affordability. When a user-requested response is unaffordable, known commands may use a retained-history cooldown and charge the invoker into overdraft; all other requests receive only a shared-platform `👎` reaction.
- Keep preflight non-monetary and separate from SDK charging. SDK methods do not recheck affordability after paid work; every provider-accepted message continues to create and charge its per-recipient usage records through the existing SDK success path.
- Grant welcome credits once, atomically, when either a Telegram or WhatsApp account is created, using the same transaction sequence on both platforms. Keep model authorization EULA/waitlist-gated.
- Make the first false-to-true EULA acceptance notification-only for the already-created grant. Notify only when the configured welcome amount is greater than zero, without comparing it to the user's current balance. Remove the obsolete grant-eligibility window.
- Keep the reviewed sequential per-chat/per-recipient reconciliation contract: only WhatsApp `sent` pricing is monetary input, paid delivery preserves the estimate, free delivery becomes zero, and the usage row remains present and reconciled.
- Keep failed/delivered/read status accounting, provider-message-ID matching, callback inboxes, price-snapshot schemas, category repricing, retry blocking, reservations, and exceptional retention out of scope.
- Produce a root `CHANGES.md` frontend handoff covering every backend contract and semantic change that may affect `agent-web`, informed by the current sibling frontend implementation.
- Generate and review the additive `usage_records.is_delivery_reconciled` migration only after the implementation milestones are approved.

## Capabilities

### New Capabilities

- `integration-delivery-pricing`: Explicit Telegram and WhatsApp delivery prices, recipient-market lookup, rounding, and stable usage identities.
- `integration-delivery-accounting`: Delivery affordability, accepted-send charging, per-recipient usage, sequential `sent` reconciliation, and ordinary retention behavior.
- `welcome-credit-onboarding`: Atomic welcome grants at account creation and notification-only first EULA acceptance.

### Modified Capabilities

None. No existing base capability specifications are present.

## Impact

- Pricing configuration and delivery tool/provider catalogs.
- Spending preflight, usage accounting, Telegram and WhatsApp SDK send boundaries, and WhatsApp status ingestion.
- Telegram and WhatsApp account creation, credit-transfer bookkeeping, settings/EULA handling, and welcome-credit configuration.
- Existing usage API documentation for the `message_delivery` purpose and reconciliation field.
- A root `CHANGES.md` handoff for frontend-visible identities, fields, semantics, and onboarding behavior; frontend implementation itself remains out of scope.
- One additive Alembic migration generated by the user; no new tables or provider-message-ID columns.
